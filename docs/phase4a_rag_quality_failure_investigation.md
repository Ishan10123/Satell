# Satell Phase 4A — Read-only RAG Quality Failure Investigation

Investigation date: 2026-11-18. Scope: read-only review of the Phase 3 reports/artifact, RAG source code, API process logs, and current Qdrant payloads. No code, tests, settings, approvals, manifest, or Qdrant data were changed.

## Executive findings

- The Phase 3 sample has all 20 exact questions, 160 ranked retrieval-hit records, final returned answer/status, citations for accepted answers, summary diagnostics, and timing data. It does **not** retain raw model text for rejected queries, parsed citation IDs for those failed generations, line-level citation errors, or claim-verifier verdict text for partially verified responses.
- The API container had four log lines since startup; none contained query text, generation prompts, citation errors, or verifier data. `scripts/run_api.py` sets `uvicorn.run(..., access_log=False)`. This confirms there is no retained raw generation log to recover for these requests.
- All 160 recorded hit chunk IDs resolve to 133 distinct current Qdrant points. Rebuilding context from the captured hit order/scores, those point payloads, current policy metadata, and the same `ContextAssembler` reproduces the saved admitted count, excluded count, and byte-budget estimate for **all 20/20 queries**. This is a deterministic reconstruction from current points, not a timestamped copy of the original prompt/context transcript.
- Each query retrieved 8 candidates; **85 chunks were admitted and 75 omitted**, all omitted for `context_budget`. No saved diagnostic indicates authorization filtering, malformed payload, duplicate chunk, or empty text as an exclusion cause.
- The eight rejected requests fail before claim verification: Q3/Q6/Q9/Q11/Q13/Q18 hit the per-claim citation-coverage gate (`uncited_claim_rejected`); Q15/Q20 hit the citation-ID gate (`citation_validation_failed`). The verifier status is `not_run` for all eight.
- Three partial answers passed citation validation and reached claim verification: Q4 6/7 supported, Q12 6/7, Q14 3/6. The exact rejected claim text/verdict row was not persisted.
- Q17 was incorrectly labeled `verified` even though its rendered answer states both that regular dictionaries iterate in arbitrary order and that insertion order is guaranteed since Python 3.7. The cited chunks explain the historical transition, but the generated answer fails to qualify its first statement. The verifier assesses claims independently and has no cross-claim contradiction check.

## Evidence sources and limits

All four Phase 3 Markdown reports and the complete JSON artifact were read. The artifact’s `answer` field is the final response saved by the Django workflow: for the eight failed rows, it is the safe local-demo abstention, not the pre-validation Ollama answer. The `diagnostics` on those rows contains only a coarse failure code/stage and `claim_verifier_status=not_run`. For partial rows, the `answer` contains only supported claims and a generic omission notice; it does not include rejected claims or verdict explanations.

Consequently, the investigation can establish the exact stage and gate that rejected each response, but cannot state the exact pre-validation answer, which [S#] labels the model emitted on failed requests, or the exact individual claims the verifier rejected. It does not recreate those generations by rerunning the model; a rerun would be a new nondeterministic result, not evidence of the original generation.

The current-Qdrant reconstruction matched all persisted aggregate context diagnostics. It gives the exact current payloads by captured chunk ID and recorded rank. The project does not contain a historical payload snapshot/hash linked to the Phase 3 run, so the report treats full-text reconstruction as strong corroboration rather than proof of historical byte identity.

### Rejection classification

- Q3, Q6, Q9, Q11, Q13, Q18: `OllamaGenerator.generate` first found at least one citation ID and found every extracted ID in the assembled context’s allowed citation IDs; it then raised `UncitedClaimError` because at least one sentence/claim failed `_all_claims_have_citations`. This makes the category a missing-per-claim-citation/format-coverage failure. The citation IDs themselves are not present in the saved artifact.
- Q15, Q20: `CitationValidationError` was raised before the per-claim coverage check. The code raises this when no `[S#]` IDs are parsed **or** any parsed ID is not in the context’s allowed IDs. The artifact does not distinguish those subreasons, so neither “no citations” nor “invalid mapping” can be claimed as the exact cause.
- These are generation-output/citation-validation failures, not verifier failures. Retrieval/context quality is a contributing factor for Q11/Q13/Q15 and potentially Q9/Q20; Q3/Q6/Q18 had direct topic evidence admitted. None of the eight show an authorization exclusion.

## Priority 3 — Q17 contradiction

Original question: In Python dictionaries, what ordering behavior is documented?

The saved answer is marked `verified` with 16/16 claims supported. It includes these conflicting statements:

> “Regular Python dictionaries iterate over key/value pairs in arbitrary order.” [S1]
> “The built-in `dict` class gained the ability to remember insertion order starting in Python 3.7.” [S2]

Citation mapping and context evidence:
- S1: `python_3_13`, document `3c40c468d2896da2fd9f18e9c9a2b58b6b4b1f39951ba931562cd007535b4fe9`, chunk `74e60577c9f9ab31130bd1e7923963652179fbf5b2faea420e901fbac4d8828c`, `whatsnew/3.1.html`, titled “What’s New In Python 3.1”. Its text states arbitrary dictionary order and contrasts this with the newly introduced `OrderedDict`; it is explicitly historical Python 3.1 material.
- S2: `python_3_13`, document `bb2796172cede3af9059973de5377799162c8bf1e9f8c50f56d566e31ff51412`, chunk `d70058a7fad475232a48686dfd3f1a87260101c206d354850130923575d28c65`, `library/collections.html`. It says regular `dict` gained insertion-order memory with that behavior guaranteed in Python 3.7.
- S3: document `3868e35992cdb7230f058b44218b8507e7bb0bb6105326cc0305bb0edcb65571`, chunk `ffcd79050e5cebf71a543734681a38c9f951755dd429d38333eb423f35e31823`, `whatsnew/3.8.html`, also says regular dicts have guaranteed ordering since Python 3.7.

The answer’s first statement is accurate only as a historical statement about pre-3.7 behavior, but it is unqualified in response to a present-tense question. It directly conflicts with the second statement in the same answer. The context contains both historical and current-version facts; the source version/context contributed to ambiguity, and generation dropped that qualification.

`LocalClaimVerifier.verify` receives a list of claims and evidence and returns per-claim support/contradiction verdicts. The integration accepts supported claims independently and has no pairwise contradiction pass across claims. Therefore the verifier did not detect that C1 and C2 conflict. Given the question’s current/general wording, the answer should not have been labelled fully verified; it should have been corrected with an explicit version timeline or rejected/partially verified. Contradiction detection is a required evaluation item, not a reason to weaken entailment thresholds.

Failed rows have no saved `prompt_tokens_estimated` because an exception interrupts `GenerationResult`; code’s pre-request budget check fails closed if an estimate exceeds 6,656. No evidence supports increasing the context window.
- The locally reconstructed full prompt estimate for the nine failed/abstained rows was not recorded. Context and query sizes remain below the same 5,000 evidence cap, but the report does not substitute a derived value for the missing original runtime metric.

5. **Citation navigation is coarse**: 34/34 references point to one of seven generic roots; none has an anchor or page destination in returned metadata.
