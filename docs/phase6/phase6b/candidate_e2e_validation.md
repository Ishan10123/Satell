# Phase 6B candidate end-to-end validation

## Scope and isolation

A separate candidate stack was created for this test. It used the candidate Django and FastAPI images, a disposable PostgreSQL container with tmpfs storage, and a disposable Qdrant container with tmpfs storage. The isolated network had no connection to the existing `rag-postgres`, `qdrant`, or application containers. Qdrant contained one synthetic documentation point and no real-corpus data. The only host-published port was Django on `127.0.0.1:18081`; FastAPI, Qdrant, and PostgreSQL had no host port bindings.

The source and document demo registries were generated only in a temporary metadata mount for one synthetic guide. Both registry records explicitly kept `legal_review_status=pending`. The query used the candidate API’s real Ollama embedding and generation providers; it did not use the Django mock adapter. The API response had `synthetic=false` because the response was generated by the configured model, while its source document was explicitly synthetic. This is not a real-corpus result.

## Runtime and query evidence

- Candidate FastAPI `/health`: HTTP 200.
- Candidate FastAPI authenticated `/ready` in explicit local demo mode: HTTP 200.
- Invalid bearer credential to `/ready`: HTTP 401.
- Candidate production-mode `/ready` using the same `operator_authorized_unreviewed` fixture manifest: HTTP 503.
- Candidate production-mode readiness therefore did not silently fall back to demo mode.
- Synthetic Qdrant collection: `rag_docs_v2`, one point, one documentation record.
- Candidate FastAPI query: HTTP 200, one dense retrieval hit, one context chunk, one citation (`S1`), citation validation passed, verifier status `verified`.
- Generated model: `qwen3.5:4b`; embedding model: `nomic-embed-text:v1.5`.
- Candidate Django-to-FastAPI HTTP workflow query: 8.58 seconds including model generation and persistence on this run. The first query was cold. This is a single synthetic observation, not a benchmark.
- PostgreSQL contained the saved user and assistant messages, one citation snapshot, and generation metadata showing verified status. JSON export retained the citation.

## Visual browser status and limits

**Visual browser validation is incomplete.** The Windows browser-control helper stopped before interaction because it could not establish the active Chrome URL with enough confidence. No browser screenshot or visual styling check was performed. The in-app browser skill file was unavailable at its advertised path. The successful HTTP workflow is useful candidate evidence but does not satisfy the requested real-browser acceptance criterion.

The synthetic citation reference is `https://docs.example.org/synthetic-container-guide`; it is fixture metadata, not a real evidence URL. A live external citation-navigation check was not performed.

## Conclusion

The isolated HTTP integration path is functional with a synthetic fixture and real local inference. The full release acceptance is **not met** because visual browser verification is incomplete, the OpenSSL findings remain open, and the existing production corpus is still blocked by authorization. No claim is made that production RAG works or that real-corpus quality has been validated.
## Browser and test-run limits

The visual browser acceptance test did not run because the Windows browser-control helper stopped before navigation when it could not establish the active URL. The HTTP workflow did exercise CSRF and session behavior, but it does not verify CSS layout, browser rendering, or interactive client-side behavior.

The RAG candidate regression suite was run inside the candidate Linux image with read-only mounts for project tests/configuration/scripts and no network. An earlier reduced-mount attempt produced eight test-harness errors; the successful full run used all three required mounts and is the result reported above.
